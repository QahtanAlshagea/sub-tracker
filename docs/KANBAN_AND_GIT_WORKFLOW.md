# 1. مدخل: لماذا نحتاج لوحة أصلاً؟

حين يعمل شخص واحد على مشروع صغير تكفيه ذاكرته. وحين يعمل خمسة على نظام متعدد الطبقات، تصبح الذاكرة أسوأ أداة إدارة ممكنة: يتكرر العمل، ويُنسى ما لم يبدأ، ويتعطّل عضو بانتظار عضو دون أن يعلم أحد. واللوحة ليست زينة إدارية، بل هي الوسيلة التي تجعل حالة العمل مرئية للجميع في لحظة واحدة، فيُعرف من ينتظر ماذا، وأين تتكدّس المهام، ومن يحتاج مساعدة قبل أن يتأخر.

## 1-1 الفرق بين قائمة الأعمال واللوحة

**قائمة الأعمال (Backlog)** سجل بكل ما نريد إنجازه مرتباً بالأولوية، وهي تجيب عن سؤال: ماذا سننفّذ؟ ووجود بند فيها لا يعني أن أحداً بدأ به.

**اللوحة (Kanban Board)** صورة لحالة العمل الجاري، وهي تجيب عن سؤال: أين وصلت المهمة؟ ولا تدخلها مهمة إلا وهي مفهومة وجاهزة.

والقاعدة الحاكمة بينهما بسيطة: لا تُنفَّذ مهمة ليست في قائمة الأعمال، ولا تبقى في اللوحة مهمة غامضة.

# 2. بنية اللوحة المعتمدة

اعتمد الفريق ستة أعمدة:

**Backlog** — كل ما نريد إنجازه لاحقاً. شرط الدخول: وصف مختصر وقيمة واضحة. المسؤول عن ترتيبه: قائد الفريق.

**Ready for Dev** — مهام مفهومة وجاهزة للبدء فوراً. شرط الدخول: وصف كامل، ومعايير قبول، ومسؤول محدد بالاسم، وخلوّها من اعتماديات معلّقة.

**In Progress** — يجري العمل عليها الآن. شرط الدخول: وجود فرع Git مفتوح باسم المهمة. من يحرّكها: صاحب المهمة نفسه.

**Code Review** — فُتح لها طلب دمج وتنتظر المراجعة. شرط الدخول: نجاح الفحص الآلي واكتمال وصف الطلب.

**Testing / QA** — يجري التحقق الوظيفي منها ومن حالات حافتها. شرط الدخول: اعتماد المراجع للكود.

**Done** — منجزة ومدموجة ومغلقة، بعد استيفاء تعريف الإنجاز كاملاً.

## 2-1 قواعد اللوحة الملزمة

أولاً، **حدّ العمل الجاري**: لا يزيد ما لدى العضو في عمود التنفيذ عن مهمتين. ومن بلغ الحد فالأولى به أن يراجع عمل غيره لا أن يسحب مهمة ثالثة، لأن كثرة المهام المفتوحة تؤخر الجميع ولا تسرّع أحداً.

ثانياً، **السحب لا الدفع**: يسحب العضو المهمة التالية بنفسه حين يفرغ، ولا تُلقى عليه من فوق.

ثالثاً، **التحديث اليومي**: يحرّك كل عضو بطاقاته ويكتب سطراً عمّا أنجزه وما يعيقه. البطاقة التي لم تتحرك ثلاثة أيام بلا تعليق تُعدّ مهمة متعثّرة وتُناقَش.

رابعاً، **بطاقة واحدة تعني فرعاً واحداً وطلب دمج واحد**. وخلط مهمتين في فرع واحد يُفسد المراجعة ويجعل التراجع مستحيلاً.

خامساً، **المهمة المعطَّلة** تُوسم بلصيقة `blocked` مع ذكر ما تنتظره، وتبقى مكانها ولا تُعاد إلى الخلف حتى لا تضيع سياقها.

سادساً، **لا بطاقة بلا مالك** خارج قائمة الأعمال. والمالك شخص واحد لا اثنان، لأن المسؤولية المشتركة في التفاصيل الصغيرة تعني غالباً ألا يتحرك أحد.

## 2-2 إنشاء اللوحة على GitHub Projects

يفتح قائد الفريق تبويب Projects في المستودع، وينشئ مشروعاً جديداً بقالب اللوحة، ويسمّيه باسم المشروع. ثم يعدّل حقل الحالة فيحذف الأعمدة الافتراضية وينشئ الأعمدة الستة بترتيبها. ثم يضيف حقولاً مخصصة للأولوية ونقاط الجهد ونوع العمل والمالك. ثم ينشئ المهام بوصفها Issues ويربط كلاً منها باللوحة من حقل Projects داخلها. وأخيراً يفعّل الأتمتة المدمجة: إضافة أي بند جديد إلى قائمة الأعمال، ونقل البطاقة إلى المراجعة عند فتح طلب دمج، ونقلها إلى المنجَز عند إغلاق المهمة.

## 2-3 البديل على Trello

ينشئ القائد مساحة عمل للفريق ثم لوحة باسم المشروع، ويضيف القوائم الست بالأسماء ذاتها. ثم ينشئ لصائق ملوّنة للمعمارية والدومين والبيانات والواجهة والجودة والتوثيق والتعطّل والأولوية الحرجة. ولكل بطاقة: عنوان، ووصف، وقائمة تحقق تمثل معايير الاكتمال، وتاريخ استحقاق، ومالك. ويُلصق رابط المهمة على GitHub داخل وصف البطاقة، حتى لا تنفصل أداة المتابعة عن أداة الشيفرة فتتناقض النسختان.

**C-06 | إعداد التكامل المستمر** — أولوية عالية، جهد 3، يعتمد على C-01 وC-02. تشغيل التنسيق والتحليل والاختبارات والتغطية آلياً على كل طلب دمج. ويكتمل حين يُحجب دمج طلب اختباراته راسبة دون تدخل بشري.

# 4. دورة العمل على Git وGitHub

## 4-1 التهيئة لمرة واحدة

يضبط كل عضو على جهازه اسمه وبريده المطابقين لحسابه على GitHub، ويجعل اسم الفرع الافتراضي `main`، ويفعّل إعادة الأساس عند السحب ليبقى تاريخ المشروع نظيفاً:

```bash
git config --global user.email "البريد@example.com"

```

## 4-2 بروتوكول الفروع

الفرع `main` نسخة مستقرة قابلة للتسليم، ولا يكتب عليه أحد مباشرة. والفرع `develop` فرع التكامل اليومي، ولا يُكتب عليه إلا عبر طلبات دمج. وأما فروع العمل فتُسمى بنمط ثابت يربط الفرع بمهمته: `feature/issue-9-domain-usecases` أو `fix/issue-33-end-of-month-due-date` أو `docs/issue-4-srs-document`. والتسمية ليست شكلية، فهي ما يجعل قراءة تاريخ المشروع بعد شهور ممكنة.

## 4-3 الدورة اليومية

```bash
git checkout develop
git pull origin develop
git checkout -b feature/issue-9-domain-usecases

# بعد العمل، راجع ما غيّرته قبل أي التزام
git status
git diff

git add lib/features/subscriptions/domain/
git commit -m "feat(domain): add AddSubscription use case with validation

- تنفيذ عقد إضافة الالتزام
- التحقق من القيمة الموجبة وطول الاسم
- اختبارات تغطي حالات الحافة المرتبطة

Refs #9"

git push -u origin feature/issue-9-domain-usecases

# قبل فتح طلب الدمج، زامن مع فرع التطوير
git fetch origin
git rebase origin/develop
git push --force-with-lease
```

## 4-4 معايير رسائل الالتزام

تُكتب الرسالة بالصيغة `النوع(النطاق): وصف موجز بصيغة الأمر`. والأنواع المعتمدة: `feat` لميزة جديدة، و`fix` لإصلاح خلل، و`test` للاختبارات، و`refactor` لإعادة الهيكلة دون تغيير سلوك، و`docs` للتوثيق، و`chore` لأعمال التهيئة، و`style` للتنسيق، و`perf` لتحسين الأداء. ولا يتجاوز السطر الأول اثنين وسبعين حرفاً، ويُذكر رقم المهمة في التذييل. وتُرفض رسائل مثل «تحديث» و«إصلاح» و«نهائي»، لأنها لا تخبر القارئ بشيء بعد أسبوع واحد.

## 4-5 طلب الدمج

يُفتح الطلب من فرع العمل إلى `develop` لا إلى `main`. ويحمل عنواناً بالصيغة نفسها، ووصفاً يذكر رقم المهمة التي يغلقها، وما الذي تغيّر، وكيف جُرّب، وأي حالات حافة غُطّيت، ولقطات شاشة إن كان العمل في الواجهة. ويُرفق به الكاتب قائمة تحقق ذاتية: خلوّ التحليل من التحذيرات، ونجاح الاختبارات، وخلوّ الدومين من استيرادات محظورة، واقتصار الملفات المتغيرة على نطاق المهمة، وتحديث الوثيقة المتأثرة. ثم يعيّن مراجعاً، وينقل البطاقة إلى عمود المراجعة، ولا يدمج بنفسه قبل الموافقة.

## 4-6 قائمة فحص المراجع

يتحقق المراجع من اثني عشر بنداً: أن الملفات المتغيرة تخص المهمة وحدها؛ وأن طبقة الدومين خالية من استيرادات إطار العرض أو محرك التخزين؛ وأن اتجاه التبعية سليم؛ وأن الجدول وكائن الوصول ومصدر البيانات والمستودع في ملفات منفصلة؛ وأن الاستثناءات منخفضة المستوى تُحوَّل إلى إخفاقات دومين؛ وأن كل منطق جديد له اختبار وأن حالات الحافة مغطاة بمعرّفاتها؛ وأن التسمية معبّرة؛ وألا يوجد تكرار منسوخ لمنطق قائم؛ وأن الأداء سليم فلا استعلام داخل حلقة ولا عمل ثقيل على الخيط الرئيسي؛ وأن الشاشة تغطي حالاتها الأربع وتستوفي التباين والوصولية؛ وألا تُسجَّل بيانات مالية في سجلات التصحيح؛ وأن التوثيق المتأثر محدَّث.

وللمراجعة آدابها: يُعلَّق على الكود لا على الشخص، ويُقترح بديل محدد بدل الاكتفاء بالاعتراض، ويُميَّز بين ما هو إلزامي وما هو مجرد رأي. والمراجع لا يوافق على ما لم يفهمه، لأن الموافقة الصامتة تنقل المسؤولية دون أن تنقل الفهم.

## 4-7 بعد الدمج

يُدمج الطلب من واجهة GitHub بخيار الدمج المضغوط ليبقى تاريخ الفرع الرئيسي نظيفاً، ثم يحدّث العضو نسخته المحلية ويحذف فرع المهمة محلياً وعلى الخادم، فالفروع الميتة المتراكمة تُربك من يأتي بعدك.

```bash
git checkout develop
git pull origin develop
git branch -d feature/issue-9-domain-usecases
git push origin --delete feature/issue-9-domain-usecases
```

## 4-8 معالجة المواقف الشائعة

من التزم على الفرع الرئيسي محلياً بالخطأ ينشئ فرعاً من موضعه الحالي ثم يعيد الفرع الرئيسي إلى حالته البعيدة. ومن أراد التراجع عن آخر التزام مع بقاء تعديلاته يستعمل إعادة الضبط الناعمة. ومن واجه تعارضاً يفتح الملف ويحذف علامات التعارض ويختار المحتوى الصحيح ثم يكمل إعادة الأساس. ومن رُفض دفعه لأن الفرع محمي فذلك هو السلوك الصحيح لا خطأ، وعليه أن يفتح طلب دمج. ومن أضاع عملاً بعملية خاطئة يستعين بسجل المراجع للعودة إلى النقطة السابقة، فالعمل الملتزَم به نادراً ما يضيع فعلاً.

# 5. طقوس الفريق وتعريف الإنجاز

## 5-1 الطقوس

وقفة يومية لا تتجاوز عشر دقائق يذكر فيها كل عضو ما أنجزه وما سينجزه وما يعيقه. وجلسة تنقيح أسبوعية لنصف ساعة تُجهَّز فيها البطاقات القادمة حتى تدخل عمود الجاهز مكتملة. ومراجعة أسبوعية للوحة تُزال فيها العوائق ويُعاد توزيع الحمل. ولقاء جودة مرتين في الأسبوع لمتابعة التغطية وحالات الحافة. وجلسة استرجاع في نهاية كل مرحلة يُسأل فيها ثلاثة أسئلة: ما الذي نستمر فيه، وما الذي نوقفه، وما الذي نبدؤه.

## 5-2 تعريف الإنجاز

لا تنتقل بطاقة إلى عمود المنجَز حتى تتحقق ثمانية شروط مجتمعة: تحقق معايير القبول كاملة؛ وتغطية حالات الحافة المرتبطة باختبارات ناجحة؛ وخلوّ التحليل الساكن من أي تحذير؛ ونجاح جميع الاختبارات وبقاء التغطية ضمن الحدود المقررة؛ واعتماد مراجع واحد على الأقل؛ ومرور التغيير عبر طلب دمج لا عبر دفع مباشر؛ وتحديث الوثائق المتأثرة؛ وتحديث سجل استخدام الذكاء الاصطناعي إن استُعين به.

وما لم تتحقق هذه الشروط فالبطاقة ليست منجَزة، مهما بدا العمل مكتملاً في نظر صاحبه.
